# Camera Orientation Conventions in aact-cesium

This document describes the three orientation data formats encountered when
loading camera poses from Bentley ContextCapture / iTwin reality data, how each
encodes rotations, and the transforms applied to produce a consistent
**CesiumJS camera-to-world matrix** with columns = `[right, up, forward]`.

---

## Internal Convention (CesiumJS)

CesiumJS cameras are stored as a 3×3 rotation matrix in ECEF coordinates:

| Column | Meaning                                              |
| ------ | ---------------------------------------------------- |
| 0      | **right** — camera X axis in ECEF                    |
| 1      | **up** — camera Y axis in ECEF                       |
| 2      | **forward** — camera Z axis (look direction) in ECEF |

This is a **left-handed** basis (`direction × up = right`), so the matrix has
determinant −1. This is standard in CesiumJS and is not a bug.

Camera positions are always stored as ECEF `Cartesian3`.

---

## 1. CCOrientations XML

**Source**: `CCOrientations.xml` files auto-generated by ContextCapture.

**Data format**: The `<Rotation>` element contains a full 3×3 rotation matrix
(9 elements: `M_00` through `M_22`) that directly encodes **camera → world**
in ECEF. No OPK angles are used.

**Camera axis convention**: Declared by the `<CameraOrientation>` element in
the parent `<Photogroup>`. Common values:

| CameraOrientation       | Col 0    | Col 1    | Col 2        |
| ----------------------- | -------- | -------- | ------------ |
| `XRightYDown` (default) | right    | **down** | forward      |
| `XRightYUp`             | right    | up       | **backward** |
| `XLeftYDown`            | **left** | **down** | forward      |

**Transform applied** (`adjustRotationForCameraOrientation`):

- `XRightYDown` → negate column 1 (down → up)
- `XRightYUp` → negate column 2 (backward → forward)
- `XLeftYDown` → negate columns 0 and 1

After adjustment the matrix is in `[right, up, forward]` form — no further
transforms are needed since positions and rotations are already in ECEF.

**Code path**: `ProjectedImageCollection.fromCCOrientationsXml()`

## 2. FIP (Flight Input Poses) — ContextScene JSON, Geographic SRS

**Source**: ContextScene JSON files with `SpatialReferenceSystem.Definition =
"WGS84"` (EPSG:4326). These contain the raw GPS/IMU poses from the drone
flight, before bundle adjustment.

**Data format**: Each pose has `Center = {x: lon°, y: lat°, z: altMeters}`
and `Rotation = {omega, phi, kappa}` in **radians**.

**OPK rotation convention**: The OPK angles encode the rotation
**ENU → camera** using the **ZYX** Euler order:

```text
R = Rz(κ) · Ry(φ) · Rx(ω)
```

The camera frame is **X-Right, Y-Up, Z-Backward** (a standard right-handed
photogrammetric frame where Z points away from the scene).

**Why Z-backward?** In the ISPRS photogrammetric convention, the camera
coordinate system has its Z axis pointing from the projection center toward the
_rear_ of the camera (away from the scene). This is the opposite of the look
direction.

**Transform pipeline**:

1. **Build rotation matrix**: `R = opkToRotationMatrix(ω, φ, κ)` — ZYX order.
2. **Transpose**: `R^T` converts ENU→camera to camera→ENU.
3. **Multiply by enuToEcef**: `cameraToWorld = enuToEcef · R^T` converts
   camera→ENU to camera→ECEF.
4. **Horizontal reflection of columns 1 and 2**: Corrects the 180° heading
   error caused by Z-backward. For each column `c`:
   ```text
   reflected = −c + 2·(c · ûp)·ûp
   ```
   where `ûp` is the local up vector (column 2 of `enuToEcef`). This negates
   the horizontal (East/North) component while preserving the vertical (Up)
   component, effectively converting backward → forward and preserving up.

**Result**: `[right, up, forward]` in ECEF. Validated at 0.0° heading and
pitch error against EXIF gimbal data for all five ground-truth test cameras.

**Code path**: `ProjectedImageCollection.fromContextSceneJson()`, geographic
SRS branch.

## 3. Calib (Calibrated / Bundle-Adjusted) — ContextScene JSON, ECEF SRS

**Source**: ContextScene JSON files with `SpatialReferenceSystem.Definition =
"EPSG:4978"`. These contain the bundle-adjusted poses — positions and
orientations have been refined to minimize reprojection error and match the
reconstructed 3D mesh.

**Data format**: Each pose has `Center = {x, y, z}` in ECEF meters and
`Rotation = {omega, phi, kappa}` in **radians**.

**OPK rotation convention**: The OPK angles encode a **camera → ECEF**
rotation using the **XYZ** Euler order:

```text
R = Rx(ω) · Ry(φ) · Rz(κ)
```

This is the **reversed** rotation order compared to FIP. The camera frame is
**X-Right, Y-Down, Z-Forward** — the standard computer vision convention.

**How this was discovered**: Systematic comparison of all five ground-truth
test cameras showed that the standard photogrammetric order `Rz·Ry·Rx`
produced large orientation errors (52–170°) for the ECEF data, while the
reversed order `Rx·Ry·Rz` produced 0.0° error for all four level cameras.
The nadir camera showed a 6.7° pitch difference from EXIF, attributable to
bundle adjustment refinement.

**Transform pipeline**:

1. **Build rotation matrix with negated angles**:
   `R' = opkToRotationMatrix(−ω, −φ, −κ)` using the standard ZYX function.
2. **Transpose**: `R'^T = Rx(ω) · Ry(φ) · Rz(κ)` — this algebraic identity
   gives us the XYZ-order matrix using the existing ZYX function.
3. **Negate column 1**: Converts camera-down to camera-up, matching the
   CesiumJS `[right, up, forward]` convention.

No `enuToEcef` multiplication is needed — the rotation is already in the ECEF
frame.

**Result**: `[right, up, forward]` in ECEF. Validated against EXIF at 0.0°
error for all four level cameras. The Calib orientations also match the tilted
3D mesh reconstruction, making them the correct choice when the mesh has a
non-level alignment.

**Code path**: `ProjectedImageCollection.fromContextSceneJson()`, ECEF SRS
branch.

## Key Insights

### The 180° Heading Error (FIP)

The photogrammetric Z-backward convention means column 2 of the raw
camera→world matrix points _away from_ the scene. A naive interpretation would
produce headings that are 180° off. The horizontal reflection fixes this by
flipping the horizontal component of the backward vector to produce forward,
while preserving the vertical component (important for oblique/nadir cameras).

### Why Calib Uses a Different Rotation Order

ContextCapture's bundle adjustment outputs poses in ECEF using the reversed
Euler order `Rx·Ry·Rz` (XYZ) rather than the photogrammetric standard
`Rz·Ry·Rx` (ZYX). The matrix encodes **camera → ECEF** directly in the
computer vision convention (X-right, Y-down, Z-forward), not the
photogrammetric convention (X-right, Y-up, Z-backward). This was determined
empirically — the ContextScene JSON does not document the convention.

### The opkToRotationMatrix Reuse Trick

Since `Rx(ω)·Ry(φ)·Rz(κ) = [Rz(−κ)·Ry(−φ)·Rx(−ω)]^T`, we can compute the
XYZ-order matrix by calling the existing ZYX function with negated angles and
transposing. This avoids duplicating the rotation matrix construction code.

### det = −1 is Expected

All three code paths produce matrices with determinant −1. This is because
CesiumJS cameras use a left-handed basis (`direction × up = right`). The
`Camera` class enforces this via `Cartesian3.cross(direction, up, right)`.
Attempting to "fix" this to det = +1 would break the camera convention.

(ground→camera vs camera→world). Despite this, both produce correct
orientations when processed through their respective pipelines.
